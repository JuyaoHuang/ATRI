# Cloud Deployment (Non-Docker) Guide

This document describes how to deploy ATRI directly on a server without using Docker. The recommended production structure is:

- Backend FastAPI hosted by `systemd`, listening on `127.0.0.1:8430`.
- Frontend built as static files with Vite, served directly by the host Nginx.
- Public entry point only exposes Nginx's `80/443`.
- Frontend and backend share the same domain, routed by path.

Recommended access structure:

```text
https://your-domain/              -> Frontend pages
https://your-domain/api/*         -> Backend API
https://your-domain/ws            -> Backend WebSocket
https://your-domain/static/*      -> Backend static resource compatibility path
https://your-domain/health        -> Backend health check
```

## 1. Environment Requirements

The server needs to have the following pre-installed:

- Python `>= 3.11`
- [uv](https://docs.astral.sh/uv/)
- Node.js `>= 18`
- npm `>= 9`
- Nginx
- HTTPS certificate, e.g., generated by Let's Encrypt / Certbot

Recommended deployment directory:

```text
/opt/atri
```

## 2. Get the Code

First deployment:

```bash
cd /opt
git clone --recurse-submodules https://github.com/JuyaoHuang/atri.git
cd atri
```

If the repository has already been cloned, initialize or update the frontend submodule:

```bash
git submodule update --init --recursive
```

The frontend submodule is located at:

```text
frontend/
```

If this directory is empty, the frontend cannot be built.

## 3. Configure Environment Variables

Create `.env`:

```bash
cp .env.example .env
```

At minimum, you need to fill in:

```env
SILICONFLOW_API_KEY=sk-xxxx
SILICONFLOW_BASE_URL=https://api.siliconflow.cn/v1
SILICONFLOW_MODEL=deepseek-ai/DeepSeek-V3.2
COMPRESS_API_KEY=sk-xxxx
JWT_SECRET_KEY=replace-with-a-long-random-secret
```

If using mem0 SaaS, you need to fill in:

```env
MEM0_API_KEY=m0-xxxx
```

If enabling GitHub OAuth, you need to fill in:

```env
GITHUB_CLIENT_ID=xxxx
GITHUB_CLIENT_SECRET=xxxx
```

`.env` contains secrets, do not commit to Git.

## 4. Install Backend Dependencies

Execute in the `atri` root directory:

```bash
uv sync
```

Test if the backend can start:

```bash
uv run python -m src.main
```

After seeing the service listening on `8430`, you can press `Ctrl+C` to stop and continue configuring `systemd`.

## 5. Use systemd to Host the Backend

Create the service file:

```bash
sudo nano /etc/systemd/system/atri.service
```

Write the following:

```ini
[Unit]
Description=ATRI FastAPI Backend
After=network.target

[Service]
Type=simple
WorkingDirectory=/opt/atri
EnvironmentFile=/opt/atri/.env
ExecStart=/usr/local/bin/uv run python -m src.main
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
```

If your `uv` is not at `/usr/local/bin/uv`, first confirm the path:

```bash
which uv
```

Then replace the path in `ExecStart` with the actual path.

Enable and start the service:

```bash
sudo systemctl daemon-reload
sudo systemctl enable atri
sudo systemctl start atri
sudo systemctl status atri
```

View logs:

```bash
journalctl -u atri -f
```

Verify the backend:

```bash
curl http://127.0.0.1:8430/health
```

Expected response:

```json
{"status":"ok"}
```

## 6. Build the Frontend

Enter the frontend submodule:

```bash
cd /opt/atri/frontend
npm ci
```

For production, it is recommended to use same-origin path building:

```bash
VITE_API_BASE_URL=/ VITE_WS_URL=/ws npm run build
```

Build output is located at:

```text
/opt/atri/frontend/dist
```

Same-origin path means:

```text
/api/...  -> Backend API
/ws       -> Backend WebSocket
```

Therefore, when changing the domain, you usually don't need to rebuild the frontend, as long as Nginx still routes by path.

If you use Windows PowerShell to build on the server, environment variable syntax is different:

```powershell
$env:VITE_API_BASE_URL="/"
$env:VITE_WS_URL="/ws"
npm run build
npx vite build 
vue-tsc -b # Vue version of tsc (TypeScript compiler), understands .vue file <template> and <script> types, does not produce compiled files, only checks for type errors
```

## 7. Configure Host Nginx

Create Nginx configuration:

```bash
sudo nano /etc/nginx/conf.d/atri.conf
```

Write and replace the domain and certificate paths:

```nginx
map $http_upgrade $connection_upgrade {
    default upgrade;
    '' close;
}

server {
    listen 80;
    server_name your-domain;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl http2;
    server_name your-domain;

    client_max_body_size 100m;

    ssl_certificate /path/to/fullchain.pem;
    ssl_certificate_key /path/to/privkey.pem;

    root /opt/atri/frontend/dist;
    index index.html;

    location /ws {
        proxy_pass http://127.0.0.1:8430;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $connection_upgrade;
        proxy_read_timeout 3600s;
        proxy_send_timeout 3600s;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    location /api/ {
        proxy_pass http://127.0.0.1:8430;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    location /static/ {
        proxy_pass http://127.0.0.1:8430;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    location /health {
        proxy_pass http://127.0.0.1:8430;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

Check and reload Nginx:

```bash
sudo nginx -t
sudo systemctl reload nginx
```

## 8. Authentication Configuration

If authentication is enabled in `config/auth.yaml`:

```yaml
enabled: true
```

For production, you need to modify the callback URLs:

```yaml
github:
  callback_url: https://your-domain/api/auth/callback

frontend:
  callback_url: https://your-domain/auth/callback
  login_url: https://your-domain/login
```

The Authorization callback URL in GitHub OAuth App must be consistent:

```text
https://your-domain/api/auth/callback
```

For personal local deployment or intranet deployment, you can disable authentication:

```yaml
enabled: false
```

After modifying `config/auth.yaml` or `.env`, restart the backend:

```bash
sudo systemctl restart atri
```

## 9. Data and Backup

For non-Docker deployment, runtime data is saved directly in the project directory:

| Path | Purpose |
|---|---|
| `data/` | Chat records, character memories, avatars, Live2D models, Qdrant local data |
| `models/` | ASR and other local model files |
| `prompts/persona/` | Character persona files |
| `.env` | Environment variables and secrets |
| `config/` | Layered configuration files |

It is recommended to regularly backup:

```bash
tar -czf atri-backup.tar.gz data models prompts/persona config .env
```

Note: `.env` may contain API Keys, OAuth Secrets, JWT Secrets. Backup files need to be stored securely.

## 10. Update Deployment

Pull updates:

```bash
cd /opt/atri
git pull
git submodule update --init --recursive
```

Update backend dependencies:

```bash
uv sync
sudo systemctl restart atri
```

Update frontend:

```bash
cd /opt/atri/frontend
npm ci
VITE_API_BASE_URL=/ VITE_WS_URL=/ws npm run build
sudo systemctl reload nginx
```

If only `.env` or `config/` was modified, you usually only need:

```bash
sudo systemctl restart atri
```

## 11. Common Issues

### 11.1 Frontend page can open, but API requests fail

First check the backend:

```bash
curl http://127.0.0.1:8430/health
```

Then check Nginx reverse proxy:

```bash
curl https://your-domain/health
```

If the backend is unavailable, check the logs:

```bash
journalctl -u atri -f
```

### 11.2 WebSocket connection fails

Confirm that `/ws` in Nginx has the following configured:

```nginx
proxy_http_version 1.1;
proxy_set_header Upgrade $http_upgrade;
proxy_set_header Connection $connection_upgrade;
```

If authentication is enabled, the frontend must complete login first before WebSocket will carry a valid JWT.

### 11.3 OAuth login redirect fails

Check if three addresses are consistent:

- `config/auth.yaml`'s `github.callback_url`
- GitHub OAuth App's Authorization callback URL
- Nginx's `/api/` reverse proxy rule

Same-domain production recommendation:

```text
https://your-domain/api/auth/callback
```

### 11.4 Frontend still requests old domain

If the frontend was built with a full domain, e.g.:

```bash
VITE_API_BASE_URL=https://old.example.com
```

Then the build output will hardcode the old address. It is recommended to rebuild using same-origin paths:

```bash
VITE_API_BASE_URL=/ VITE_WS_URL=/ws npm run build
```

### 11.5 404 after page refresh

Confirm that Nginx's frontend routing configuration is:

```nginx
location / {
    try_files $uri $uri/ /index.html;
}
```

This is a necessary configuration for Vue Router frontend routing in production.

### 11.6 Port exposed to public network

Production environment recommends only exposing Nginx's `80/443`. Backend `8430` should only allow localhost access.

You can use a firewall to restrict, or ensure the backend is only accessible by Nginx through `127.0.0.1:8430`.
