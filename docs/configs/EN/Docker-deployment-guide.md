# Docker Deployment Guide

This document describes how to deploy ATRI using Docker. The currently recommended production deployment approach is:

- The backend runs in Docker and is available only as `backend:8430` on the internal
  Compose network; it is not published to the host.
- The frontend is built as static files. Nginx in the frontend container serves the pages and
  proxies the backend through the unified host entry point at `127.0.0.1:5200`.
- The host Nginx handles HTTPS and the domain, forwarding all traffic to `127.0.0.1:5200`.
- Frontend and backend share the same domain, distinguished by path.

Recommended access structure:

```text
https://your-domain/              -> Frontend pages
https://your-domain/api/*         -> Backend API
https://your-domain/ws            -> Backend WebSocket
https://your-domain/static/*      -> Backend static resource compatibility path
https://your-domain/health        -> Backend health check
```

## 1. Related Files

Docker deployment related files are located in the `atri` main repository:

| File | Purpose |
|---|---|
| `Dockerfile` | Backend image definition, installs Python dependencies and starts FastAPI |
| `docker-compose.prod.yml` | Production environment orchestration, starts backend and frontend containers |
| `.dockerignore` | Excludes virtual environments, secrets, runtime data, and build artifacts |
| `docker/frontend.Dockerfile` | Frontend build image, builds Vite output and hands it to Nginx |
| `docker/frontend-nginx.conf` | Nginx configuration inside the frontend container |
| `docker/host-nginx.same-domain.conf` | Host same-domain reverse proxy example |

## 2. Environment Requirements

The server needs to have the following pre-installed:

- Docker
- Docker Compose v2
- Nginx
- HTTPS certificate, e.g., generated by Let's Encrypt / Certbot

Verify Docker Compose is available:

```bash
docker compose version
```

## 3. Get the Code

For first deployment, it is recommended to directly clone with submodules:

```bash
git clone --recurse-submodules https://github.com/JuyaoHuang/atri.git
cd atri
```

If the repository has already been cloned, initialize or update the frontend submodule:

```bash
git submodule update --init --recursive
```

The frontend submodule is located at:

```text
frontend/
```

If this directory is empty, the frontend image build will fail.

## 4. Configure Environment Variables

Create `.env` from the template:

```bash
cp .env.example .env
```

At minimum, you need to fill in:

```env
SILICONFLOW_API_KEY=sk-xxxx
SILICONFLOW_BASE_URL=https://api.siliconflow.cn/v1
SILICONFLOW_MODEL=deepseek-ai/DeepSeek-V3.2
COMPRESS_API_KEY=sk-xxxx
JWT_SECRET_KEY=replace-with-a-long-random-secret
```

If using mem0 SaaS, you need to fill in:

```env
MEM0_API_KEY=m0-xxxx
```

If enabling GitHub OAuth, you need to fill in:

```env
GITHUB_CLIENT_ID=xxxx
GITHUB_CLIENT_SECRET=xxxx
```

`.env` contains secrets, do not commit to Git.

## 5. Authentication Configuration

If authentication is enabled in `config/auth.yaml`:

```yaml
enabled: true
```

You need to change the OAuth callback URL to the production domain:

```yaml
github:
  callback_url: https://your-domain/api/auth/callback

frontend:
  callback_url: https://your-domain/auth/callback
  login_url: https://your-domain/login
```

The Authorization callback URL in GitHub OAuth App must be consistent:

```text
https://your-domain/api/auth/callback
```

If deploying locally or on an intranet, you can keep:

```yaml
enabled: false
```

When authentication is disabled, GitHub OAuth configuration is not needed.

## 6. Frontend Build Parameters

`docker-compose.prod.yml` defaults to using same-domain paths:

```yaml
args:
  VITE_API_BASE_URL: /
  VITE_WS_URL: /ws
```

This means the frontend will request:

```text
/api/...
/ws
```

Nginx in the frontend container forwards `/api/`, `/ws`, backend static assets, health checks,
and API documentation to `backend:8430`. Therefore, changing the production domain usually
does not require rebuilding the frontend image; the host Nginx only needs to keep forwarding the
unified entry point to `127.0.0.1:5200`.

If you change to different domains for frontend and backend in the future, change the build parameters to full addresses:

```yaml
args:
  VITE_API_BASE_URL: https://api.example.com
  VITE_WS_URL: wss://api.example.com/ws
```

Different domain deployment also requires additional CORS configuration.

## 7. Start Services

Execute in the `atri` root directory:

```bash
docker compose -f docker-compose.prod.yml build
docker compose -f docker-compose.prod.yml up -d
```

Check container status:

```bash
docker compose -f docker-compose.prod.yml ps
```

View backend logs:

```bash
docker compose -f docker-compose.prod.yml logs -f backend
```

View frontend logs:

```bash
docker compose -f docker-compose.prod.yml logs -f frontend
```

Stop services:

```bash
docker compose -f docker-compose.prod.yml down
```

## 8. Persistent Directories

`docker-compose.prod.yml` mounts the following directories:

| Host Path | Container Path | Purpose |
|---|---|---|
| `./data` | `/app/data` | Chat records, character memories, avatars, Live2D models, Qdrant local data |
| `./models` | `/app/models` | ASR and other local model files |
| `./prompts/persona` | `/app/prompts/persona` | Character persona files |
| `./config` | `/app/config` | Authentication, ASR, TTS, VAD, vision, and other runtime settings |

These directories are preserved after container rebuild. When backing up project data, prioritize backing up:

```text
data/
models/
prompts/persona/
.env
config/
```

`.env` and `config/` may contain sensitive configurations; pay attention to permissions when backing up.

## 9. Host Nginx Configuration

Copy the example configuration:

```bash
sudo cp docker/host-nginx.same-domain.conf /etc/nginx/conf.d/atri.conf
```

Edit `/etc/nginx/conf.d/atri.conf`:

- Replace `example.com` with your domain.
- Change `ssl_certificate` to the certificate path.
- Change `ssl_certificate_key` to the private key path.

Core forwarding rules:

```nginx
location /ws {
    proxy_pass http://127.0.0.1:5200;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection $connection_upgrade;
}

location / {
    proxy_pass http://127.0.0.1:5200;
}
```

The host no longer accesses backend port 8430 directly. After `/api/`, `/static/`, `/health`,
`/docs`, `/redoc`, `/openapi.json`, and `/ws` reach the frontend container,
`docker/frontend-nginx.conf` forwards them to `backend:8430` on the Compose network.

Check and reload Nginx:

```bash
sudo nginx -t
sudo systemctl reload nginx
```

## 10. Update Deployment

Update the main repository and frontend submodule:

```bash
git pull
git submodule update --init --recursive
```

Rebuild and start:

```bash
docker compose -f docker-compose.prod.yml build
docker compose -f docker-compose.prod.yml up -d
```

If only `.env` or `config/` was modified, you usually don't need to rebuild the image, just restart the backend:

```bash
docker compose -f docker-compose.prod.yml restart backend
```

If frontend code or frontend environment variables were modified, you need to rebuild the frontend image.

## 11. Common Issues

### 11.1 Frontend can open, but API requests fail

Check the public unified entry point:

```bash
curl https://your-domain/health
```

You can also bypass the host Nginx and check the frontend container's unified entry point:

```bash
curl http://127.0.0.1:5200/health
```

To check the backend directly, run the check inside the Compose network:

```bash
docker compose -f docker-compose.prod.yml exec backend \
  python -c "import urllib.request; print(urllib.request.urlopen('http://127.0.0.1:8430/health').read().decode())"
```

If the backend is unavailable, check the logs:

```bash
docker compose -f docker-compose.prod.yml logs -f backend
```

### 11.2 WebSocket connection fails

Confirm that `/ws` in both the host and frontend-container Nginx has the Upgrade header configured:

```nginx
proxy_http_version 1.1;
proxy_set_header Upgrade $http_upgrade;
proxy_set_header Connection $connection_upgrade;
```

If authentication is enabled, WebSocket needs to carry a valid JWT. Please complete login on the frontend first.

### 11.3 OAuth login redirect fails

Check if three addresses are consistent:

- `config/auth.yaml`'s `github.callback_url`
- GitHub OAuth App's Authorization callback URL
- Frontend-container Nginx's `/api/` forwarding rule

Same-domain production recommendation:

```text
https://your-domain/api/auth/callback
```

### 11.4 After changing domain, frontend still requests old address

The current production configuration uses:

```yaml
VITE_API_BASE_URL: /
VITE_WS_URL: /ws
```

This configuration does not hardcode the domain. If you manually changed it to a full domain, you need to rebuild the frontend image.

### 11.5 Frontend build fails

First confirm the submodule exists and is not an empty directory:

```bash
git submodule update --init --recursive
ls frontend/package.json
```

Then rebuild:

```bash
docker compose -f docker-compose.prod.yml build frontend
```

### 11.6 Data lost after container starts

Confirm that data mounts exist in `docker-compose.prod.yml`:

```yaml
volumes:
  - ./data:/app/data
  - ./models:/app/models
  - ./prompts/persona:/app/prompts/persona
  - ./config:/app/config
```

Don't just back up images. Runtime data is in the host mount directories.
