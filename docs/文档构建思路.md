# 文档构建思路

本文定义 `docs/` 目录后续的组织方式。目标是让开发文档能同时支持三件事：

- 开始一个新功能时，能快速创建设计文档、实施文档和开发日志。
- 功能完成后，能把长期有效的结论沉淀到模块文档。
- 将来迁移到 GitHub Wiki 时，有一个清晰的本地预发布区。

## 核心原则

### 1. 先区分读者

`docs/` 下的文档按读者分为两类：

- 用户文档：安装、配置、部署、使用说明。
- 开发文档：架构、模块设计、功能开发过程、技术决策、开发复盘。

用户文档优先回答“怎么用”。开发文档优先回答“为什么这样设计，以及怎么改”。

### 2. 再区分生命周期

开发文档按生命周期分为四类：

- 稳定设计：长期有效，和代码结构绑定。
- 功能过程：某次 feature 开发期间产生的设计、计划、日志、验收。
- Wiki 发布稿：整理过、适合迁移到 GitHub Wiki 的文章。
- 历史归档：不再维护，但可能有参考价值的旧文档。

不要把这四类混在同一个目录里。

### 3. 文档位置要能从代码路径推导

如果代码在 `src/tts/`，稳定设计文档应该在：

```text
docs/developments/modules/tts/
```

如果代码在 `src/memory/`，稳定设计文档应该在：

```text
docs/developments/modules/memory/
```

这样开始改代码时，可以直接找到对应模块文档。

## 推荐目录结构

```text
docs/
├── quickstart.md                     # 中文快速开始入口
├── quickstart.en.md                  # 英文快速开始入口
├── configs/                          # 用户配置、部署、使用说明
│   ├── CN/                           # 中文用户文档
│   └── EN/                           # 英文用户文档
├── develop-blogs/                    # 历史开发文章；后续建议迁移到 developments/wiki/
└── developments/                     # 开发文档主目录
    ├── README.md                     # 开发文档导航和阅读路径
    ├── architecture/                 # 项目级架构、分层、跨模块数据流
    ├── api/                          # REST API、WebSocket、事件协议
    ├── modules/                      # 长期模块设计；目录尽量对齐 src/
    │   ├── agent/                    # ChatAgent、角色上下文、对话编排
    │   ├── asr/                      # ASR 模块接口、Provider、配置、数据流
    │   ├── auth/                     # 认证、会话、权限边界
    │   ├── frontend/                 # 前端架构、状态管理、交互协议
    │   ├── llm/                      # LLM 调用层、工厂、流式接口
    │   ├── memory/                   # 记忆系统、压缩、长期记忆、恢复策略
    │   ├── routes/                   # 路由层、接口聚合、WebSocket 入口
    │   ├── storage/                  # 存储抽象、数据模型、持久化策略
    │   ├── translate/                # 翻译模块设计和调用边界
    │   ├── tts/                      # TTS 模块接口、Provider、配置、流式方案
    │   └── vad/                      # VAD 唤醒、中断、实时语音链路
    ├── features/                     # 每次大功能开发的设计、计划、日志、验收
    │   └── 2026-07-tts-segment-streaming/ # 示例：TTS 分段流式化开发过程
    ├── wiki/                         # GitHub Wiki 本地预发布区
    │   ├── Home.md                   # Wiki 首页草稿
    │   ├── _Sidebar.md               # GitHub Wiki 侧边栏草稿
    │   ├── architecture/             # 面向 Wiki 读者的架构文章
    │   ├── development-blogs/        # 整理后的开发 blog
    │   ├── modules/                  # 面向 Wiki 读者的模块介绍
    │   └── troubleshooting/          # 问题排查和经验复盘
    ├── decisions/                    # ADR 技术决策记录
    ├── templates/                    # feature、模块设计、ADR 等文档模板
    └── archive/                      # 旧会话、旧草稿、已替代文档归档
```

## 目录职责

### `docs/configs/`

放用户能直接使用的配置、部署和功能使用说明。

适合放：

- ASR 配置说明
- TTS 配置说明
- VAD 配置说明
- Docker 部署指南
- 云端部署指南
- 角色创建指南

不适合放：

- 开发过程日志
- 模块内部设计讨论
- 未定稿的实现计划

### `docs/developments/architecture/`

放项目级架构文档。

适合放：

- 项目整体架构
- 后端分层架构
- 前端整体架构
- 核心数据流
- 跨模块工作流

这类文档回答：“系统整体长什么样？”

### `docs/developments/api/`

放稳定的接口和协议文档。

适合放：

- REST API 文档
- WebSocket 协议
- 服务端事件格式
- 前后端接口契约

这类文档回答：“模块之间怎么通信？”

### `docs/developments/modules/`

放长期有效的模块设计文档。目录名尽量对齐 `src/` 下的模块名。

示例：

```text
docs/developments/modules/tts/
├── README.zh-CN.md
├── design.zh-CN.md
├── providers.zh-CN.md
├── config.zh-CN.md
└── streaming-design.zh-CN.md
```

适合放：

- 模块职责
- 接口设计
- 工厂模式
- Provider 规范
- 配置结构
- 数据流
- 异常设计
- 测试策略

不适合放：

- 某次开发的每日日志
- 临时 debug 记录
- 已废弃的方案全文

### `docs/developments/features/`

放每一次大功能开发的全过程文档。

每个 feature 一个目录：

```text
docs/developments/features/YYYY-MM-feature-slug/
```

例如：

```text
docs/developments/features/2026-07-tts-segment-streaming/
├── README.zh-CN.md
├── design.zh-CN.md
├── implementation-plan.zh-CN.md
├── dev-log.zh-CN.md
├── acceptance.zh-CN.md
└── references.zh-CN.md
```

文件职责：

| 文件 | 职责 |
|---|---|
| `README.zh-CN.md` | feature 入口、状态、范围、相关链接 |
| `design.zh-CN.md` | 目标、边界、架构、数据流、接口、取舍 |
| `implementation-plan.zh-CN.md` | step、point、文件改动、测试计划 |
| `dev-log.zh-CN.md` | 开发过程事实、问题、修正、阶段记录 |
| `acceptance.zh-CN.md` | 验收场景、测试命令、结果、遗留问题 |
| `references.zh-CN.md` | 参考资料、相关代码、相关 issue/PR |

这类文档回答：“这次功能是怎么从想法走到落地的？”

### `docs/developments/wiki/`

这是 GitHub Wiki 的本地预发布区。

`wiki/` 里只放整理过的内容，不放原始开发流水。它应该接近可以直接迁移到 GitHub Wiki 的状态。

建议保留：

```text
docs/developments/wiki/
├── Home.md
├── _Sidebar.md
├── architecture/
├── development-blogs/
├── modules/
└── troubleshooting/
```

适合放：

- 整理后的开发 blog
- 面向外部读者的架构说明
- 经验复盘
- 常见问题排查
- 可长期阅读的模块介绍

不适合放：

- 未完成的设计草稿
- 每日开发流水
- 大段原始对话备份
- 没有整理过的临时代码片段

`develop-blogs/` 可以作为历史位置保留。后续新增开发文章，建议先在 feature 的 `dev-log.zh-CN.md` 记录，完成后整理到：

```text
docs/developments/wiki/development-blogs/YYYY-MM-DD-topic.zh-CN.md
```

### `docs/developments/decisions/`

放 ADR，也就是 Architecture Decision Record，技术决策记录。

适合记录：

- 选择某个架构方案的原因
- 放弃某个方案的原因
- 模块边界的关键决策
- 会影响后续开发的约束

命名：

```text
docs/developments/decisions/YYYY-MM-DD-title.zh-CN.md
```

示例：

```text
docs/developments/decisions/2026-07-08-use-application-level-tts-segmentation.zh-CN.md
```

### `docs/developments/templates/`

放文档模板。

建议准备：

```text
docs/developments/templates/
├── feature-readme.zh-CN.md
├── feature-design.zh-CN.md
├── implementation-plan.zh-CN.md
├── dev-log.zh-CN.md
├── acceptance.zh-CN.md
├── module-design.zh-CN.md
└── adr.zh-CN.md
```

开始新功能时，从模板复制即可。

### `docs/developments/archive/`

放历史归档。

适合放：

- 旧会话备份
- 已被新文档替代的长讨论
- 不再维护的草稿
- 仅用于追溯的历史资料

归档文档不再作为开发前必读材料。

## 命名规则

### 目录名

新目录统一使用英文 `kebab-case`。

推荐：

```text
tts-segment-streaming
voice-realtime-pipeline
memory-compression-repair
```

不推荐：

```text
TTS流式
新功能
最终版
讨论记录
```

feature 目录带年月前缀：

```text
YYYY-MM-feature-slug
```

示例：

```text
2026-07-tts-segment-streaming
```

### 文件名

新文件统一使用：

```text
purpose.locale.md
```

示例：

```text
design.zh-CN.md
design.en-US.md
implementation-plan.zh-CN.md
dev-log.zh-CN.md
acceptance.zh-CN.md
```

中文标题写在 Markdown 的 H1 中，不写进新文件名。

### 语言后缀

建议使用：

```text
zh-CN
en-US
```

如果只有中文，只写 `zh-CN` 版本即可。

### 状态标记

重要开发文档建议在文件开头写 front matter：

```markdown
---
status: draft
owner: tts
created: 2026-07-08
updated: 2026-07-08
related_code:
  - src/tts/
  - src/routes/chat_ws.py
---
```

`status` 建议使用：

| 状态 | 含义 |
|---|---|
| `draft` | 草稿，还在讨论 |
| `active` | 当前实现依据 |
| `accepted` | 已完成并被代码采用 |
| `superseded` | 已被新文档替代 |
| `archived` | 仅保留历史参考 |

## 开始新功能时的流程

### Step 1: 新建 feature 目录

例如开发 TTS 分段流式化：

```text
docs/developments/features/2026-07-tts-segment-streaming/
```

### Step 2: 先写设计和实施计划

至少创建：

```text
design.zh-CN.md
implementation-plan.zh-CN.md
```

`design.zh-CN.md` 回答：

- 为什么做？
- 不做什么？
- 数据流是什么？
- 接口怎么变？
- 和现有模块边界是什么？
- 有哪些取舍？

`implementation-plan.zh-CN.md` 回答：

- 分几个 step？
- 每个 step 改哪些文件？
- 每个 step 怎么测试？
- 哪些行为必须保持兼容？

### Step 3: 开发时持续写 dev log

开发过程中的事实写入：

```text
dev-log.zh-CN.md
```

推荐格式：

```markdown
## 2026-07-08 Step 2 文本分段器

### 完成

- 新增 `src/tts/sentence_divider.py`
- 使用 `pysbd` 做句子边界检测

### 发现

- 中文短句需要控制最小字符数，避免首包过碎。

### 下一步

- 增加 segment manager 的并发和顺序投递测试。
```

### Step 4: 完成后写验收

验收结果写入：

```text
acceptance.zh-CN.md
```

至少记录：

- 自动测试命令
- 手动验收场景
- 通过结果
- 未覆盖风险
- 后续工作

### Step 5: 提炼长期文档

功能完成后，不要让所有结论只留在 `features/` 里。

需要把长期有效的内容提炼到：

```text
docs/developments/modules/<module>/
```

例如：

```text
docs/developments/modules/tts/streaming-design.zh-CN.md
```

### Step 6: 整理 Wiki 发布稿

如果这次开发值得写成文章，从 `dev-log.zh-CN.md` 提炼到：

```text
docs/developments/wiki/development-blogs/YYYY-MM-DD-topic.zh-CN.md
```

Wiki 文章应该有清晰叙事：

- 背景
- 问题
- 方案
- 实现路径
- 踩坑
- 验收
- 后续改进

不要直接把开发流水复制到 Wiki。

## 文档选择速查表

| 我现在要写什么 | 应该放哪里 |
|---|---|
| 新功能的设计文档 | `docs/developments/features/YYYY-MM-feature/design.zh-CN.md` |
| 新功能的实施计划 | `docs/developments/features/YYYY-MM-feature/implementation-plan.zh-CN.md` |
| 新功能开发过程记录 | `docs/developments/features/YYYY-MM-feature/dev-log.zh-CN.md` |
| 新功能验收记录 | `docs/developments/features/YYYY-MM-feature/acceptance.zh-CN.md` |
| 模块长期设计 | `docs/developments/modules/<module>/design.zh-CN.md` |
| 模块接口或 Provider 规范 | `docs/developments/modules/<module>/interface.zh-CN.md` |
| REST/WebSocket 协议 | `docs/developments/api/` |
| 项目整体架构 | `docs/developments/architecture/` |
| 技术决策 | `docs/developments/decisions/YYYY-MM-DD-title.zh-CN.md` |
| 准备发布到 GitHub Wiki 的文章 | `docs/developments/wiki/` |
| 旧会话备份和过期草稿 | `docs/developments/archive/` |
| 用户配置和部署说明 | `docs/configs/` |

## 现有文档迁移建议

后续整理现有文档时，可以按下面规则迁移。

### 架构文档

```text
docs/developments/项目架构设计.md
docs/developments/project-architecture-design.en.md
```

建议迁移到：

```text
docs/developments/architecture/project-architecture.zh-CN.md
docs/developments/architecture/project-architecture.en-US.md
```

### 模块设计

```text
docs/developments/module-design/CN/TTS模块设计文档.md
```

建议迁移到：

```text
docs/developments/modules/tts/design.zh-CN.md
```

其他模块同理：

```text
module-design/CN/ASR模块设计文档.md      -> modules/asr/design.zh-CN.md
module-design/CN/LLM调用层设计讨论.md    -> modules/llm/design.zh-CN.md
module-design/CN/记忆系统设计讨论.md      -> modules/memory/design.zh-CN.md
module-design/CN/VAD语音唤醒模块设计.md  -> modules/vad/design.zh-CN.md
module-design/CN/后端API接口文档.md      -> api/backend-api.zh-CN.md
```

### 现有 `wiki/TTS` 和 `wiki/VAD`

当前 `docs/developments/wiki/TTS/` 和 `docs/developments/wiki/VAD/` 里有设计、实施和日志混放。

建议拆分：

- 长期设计：迁移到 `modules/tts/` 或 `modules/vad/`。
- 某次功能实施计划：迁移到 `features/YYYY-MM-feature/`。
- 整理后的开发文章：保留到 `wiki/development-blogs/`。
- 旧流水和不再维护记录：迁移到 `archive/`。

### 会话备份

```text
docs/developments/会话上下文备份_20260418.md
```

建议迁移到：

```text
docs/developments/archive/2026/会话上下文备份_20260418.md
```

这类文档不应作为新开发的必读入口。

## TTS 分段流式化示例

当前主线任务可以这样组织：

```text
docs/developments/features/2026-07-tts-segment-streaming/
├── README.zh-CN.md
├── design.zh-CN.md
├── implementation-plan.zh-CN.md
├── dev-log.zh-CN.md
├── acceptance.zh-CN.md
└── references.zh-CN.md
```

完成后沉淀：

```text
docs/developments/modules/tts/streaming-design.zh-CN.md
docs/developments/wiki/development-blogs/2026-07-tts-segment-streaming.zh-CN.md
```

如果这次选择“应用层分段合成，不做 provider 原生流式”，这是一个会影响后续开发的决策，也可以记录：

```text
docs/developments/decisions/2026-07-08-use-application-level-tts-segmentation.zh-CN.md
```

## README 入口规则

每个重要目录都建议有 `README.zh-CN.md` 或 `README.md`。

README 只做导航，不堆正文。

推荐内容：

- 这个目录放什么
- 不放什么
- 当前维护状态
- 子文档列表
- 开发前阅读顺序

例如 `docs/developments/README.md` 应该回答：

- 新开发者先读什么？
- 改 TTS 应该读什么？
- 改 VAD 应该读什么？
- 哪些文档是历史归档？
- 哪些文档准备迁移到 GitHub Wiki？

## 最小执行规则

如果不想一次性整理全部文档，至少先遵守这四条：

1. 新功能一律建 `docs/developments/features/YYYY-MM-feature-slug/`。
2. 模块长期设计一律放 `docs/developments/modules/<module>/`。
3. 准备发布到 GitHub Wiki 的文章一律放 `docs/developments/wiki/`。
4. 旧备份、旧讨论、过期草稿一律放 `docs/developments/archive/`。

这四条执行起来，`docs/developments` 就不会继续变乱。
